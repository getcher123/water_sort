# Архитектура Jelly Sort

Игра написана на GDScript и исполняется Godot. JavaScript используется только для Web-загрузки, сборочных скриптов и тестов загрузчика. Он не дублирует правила головоломки.

## Основные части

| Файл | Ответственность |
|---|---|
| `godot/scripts/board_model.gd` | Независимая модель `SortBoard`: уровни, допустимость хода, переливание, история, отмена, победа |
| `godot/scripts/main.gd` | Контроллер сцены: интерфейс, мышь/касания/клавиатура, состояние анимации, пауза, переходы, прогресс |
| `godot/scripts/bottle_view.gd` | Рисование колбы, маска жидкости, дробные объёмы при анимации, поверхность и блики |
| `godot/scripts/backdrop.gd` | Процедурный фон B1F1 |
| `godot/scenes/main.tscn` | Главная сцена, запускающая контроллер |
| `godot/web_shell.html` | Оболочка экспорта, проверка браузерных возможностей и транспорт WebAssembly |
| `scripts/build-web.mjs` | Импорт, проверки, Web-экспорт и подготовка статической сборки |

## Модель игрового поля

`SortBoard` наследует `RefCounted` и не зависит от интерфейса. Каждая колба хранится массивом целых идентификаторов цветов **снизу вверх**. Например, `[0, 0, 1, 2]` означает два коралловых слоя внизу, золотой над ними и бирюзовый сверху.

| ID | Цвет | Значение |
|---|---|---|
| 0 | Коралловый | `#FF7C7E` |
| 1 | Золотой | `#F5B733` |
| 2 | Бирюзовый | `#43C2C7` |
| 3 | Фиолетовый | `#9A6AE1` |

Три фиксированные раскладки используют шесть колб вместимостью четыре единицы, четыре цвета по четыре единицы и две изначально пустые колбы. Индексы в коде начинаются с нуля; клавиши интерфейса — с единицы.

Переливание допустимо, когда источник не пуст, в цели есть место, а её верхний цвет совпадает с цветом источника либо цель пуста. Переносится максимальная непрерывная группа верхнего цвета в пределах свободной вместимости цели. Нельзя переливать колбу в саму себя.

Модель хранит историю для отмены, счётчик ходов и индекс уровня. Победа наступает, когда каждая непустая колба заполнена одним цветом. Состояние может быть получено через `snapshot()`.

В тестах подтверждена решаемость всех трёх уровней. Минимальные решения: 6, 9 и 14 ходов; пути приведены в [отчёте модели](../qa/board-report.md).

## Ход и анимация

1. Контроллер получает выбор источника и цели и проверяет ход через модель.
2. Успешный ход записывается в модель **один раз**, после чего блокируется новый игровой ввод.
3. Tween перемещает и наклоняет колбу; дробные визуальные объёмы и струя показывают переливание.
4. По завершении представление синхронизируется с моделью, снимается блокировка и проверяется победа.

Правила не вычисляются заново в каждом кадре анимации. Отмена возвращает прошлое логическое состояние, а не пытается восстановить его из изображения жидкости.

Пауза, потеря фокуса, подтверждение перезапуска и смена уровня обрабатываются контроллером. При смене сценария используется защитный идентификатор анимации: завершение старого Tween не должно менять уже новое поле. Незавершённое касание сбрасывается при потере фокуса, чтобы возвращение в окно не создавало случайного хода.

## Плоская жидкость

Колба — `Node2D` с локальным началом координат в центре дна и базовыми размерами 150 × 360. Её внутренний контур задаёт U-образную маску; стеклянные стенки и блики рисуются отдельно от жидкости.

Каждая единица жидкости соответствует площади внутренней полости. Поэтому закругление дна не изменяет логический объём слоя. При наклоне колбы направление поверхности пересчитывается так, чтобы она оставалась горизонтальной относительно игрового экрана. Метод `get_liquid_surface_local()` возвращает поверхность для привязки анимированной струи.

Это управляемая 2D-имитация, подходящая для Water Sort: здесь нет трёхмерной сетки жидкости, численного гидродинамического решателя или частиц, определяющих игровые правила.

## Web-экспорт

Экспорт использует renderer **Compatibility** и отключённые потоки. Браузеру нужны WebAssembly и WebGL 2, но не SharedArrayBuffer и не специальные заголовки COOP/COEP.

После экспорта сборщик подготавливает следующие файлы:

| Файл в `dist` | Назначение |
|---|---|
| `index.html` | HTML-оболочка и экран загрузки |
| `index.js` | Стандартный JavaScript-загрузчик Godot |
| `index.pck` | Сцены, скрипты и ресурсы игры |
| `runtime-manifest.json` | Размеры, контрольные суммы и расположение частей движка |
| `engine.wasm.gz` | Сжатый транспорт исходного WebAssembly-runtime |
| `engine-part-1.bin`, `engine-part-2.bin` | Несжатый резервный транспорт runtime |
| Файлы иконок, worklet и лицензий | Сопутствующие ресурсы Web-экспорта |

Адаптер загрузки собирает исходные байты движка, проверяет размер и SHA-256 и передаёт их стандартному загрузчику. Он не переписывает игровой код или runtime Godot. Gzip-путь уменьшает первую загрузку; резервный путь нужен, если распаковка браузером недоступна.

Разделение runtime сохранено из исходной схемы статической публикации. Это свойство данного сборщика, а не утверждение о необходимости такого разделения для любого проекта GitHub Pages.

Ресурсы используют относительные URL. Это позволяет открывать игру из подпапки, в частности `/water_sort/`, без отдельного backend. При развёртывании всегда публикуется `dist` целиком; смешивание файлов разных экспортов нарушает контроль целостности.

## Прогресс и внешние зависимости

Выбранный и пройденные уровни сохраняются через `user://progress.cfg` по возможности. Незаконченная раскладка не сохраняется; очистка данных браузера может сбросить прогресс. Игрового backend, аккаунтов, API-ключей, рекламного или аналитического SDK нет.

## Где вносить изменения

| Изменение | Основное место |
|---|---|
| Правила, вместимость, новые раскладки | `board_model.gd` и тесты модели |
| Силуэт, блики, цвета и маска жидкости | `bottle_view.gd` |
| Фон | `backdrop.gd` |
| Кнопки, ввод, анимации, сохранение | `main.gd` и тесты контроллера |
| Экран загрузки и диагностика | `web_shell.html` и тесты Web-загрузчика |
| Подготовка статической сборки | `build-web.mjs` и workflow публикации |

Текущий интерфейс рассчитан на три уровня и шесть колб. При расширении модели необходимо согласованно обновить раскладку интерфейса, управление и тесты. После любых изменений в графике или вводе дополнительно нужен ручной прогон в браузере с WebGL 2: headless-проверки его не заменяют.
